# 00. スコープと設計原則

## 1. 何を作るのか

**動物病院の「入院中の動物のケア」に特化した記録・管理システム。**

一言で言うと、現場のホワイトボードと入院ノートと投薬チェック表を1つにまとめ、
**「指示されたケアが、資格を持つ人によって、時間通りに実施されたか」を機械的に追跡できるようにする**もの。

## 2. なぜ「入院」に絞るのか

動物病院向けの電子カルテ／レセコンはすでに10製品以上あり、その多くが入院管理機能を持っている（`05-market-and-competition.md`）。
それでも入院管理に絞る理由は3つ。

1. **既存製品の入院機能は、外来カルテの付属品として作られている。** 外来は「1回の来院で完結する」が、入院は「24時間×複数日×交代勤務」という別の時間構造を持つ。同じUIモデルで両方を最適化するのは難しい。
2. **入院はミスの重大性が桁違い。** 投与量の誤り、投薬の飛ばし、申し送り漏れが直接死につながる。ここは「あれば便利」ではなく「無いと怖い」領域で、対価を払う理由になる。
3. **愛玩動物看護師の国家資格化（2022年施行）で、「誰がやってよい処置か」が法的に線引きされた。** 既存製品はこの変化以前に設計されたものが多く、資格に基づく実施権限の管理は差別化余地がある。

## 3. スコープ

### Phase 1（MVP）で作るもの

| # | 機能 | 理由 |
|---|---|---|
| 1 | **ケージボード** — 全入院患畜を1画面で俯瞰 | ホワイトボードの置換。導入初日から価値が出る |
| 2 | **入院指示（CareOrder）の発行** — 獣医師のみ | すべての起点 |
| 3 | **投与量の自動計算** — 体重×mg/kg、CRI速度、上限・種別禁忌チェック | 医療安全の中核。最大の売り文句 |
| 4 | **タスク展開と実施記録** — 未実施の自動検出 | 「やったつもり」を潰す |
| 5 | **資格に基づく実施権限の強制** | 愛玩動物看護師法への対応。他社にない切り口 |
| 6 | **バイタル・IN/OUT記録とグラフ** | 日々の記録の主体 |
| 7 | **申し送り（既読管理つき）** | 夜間交代の事故防止 |
| 8 | **監査ログと記録の不変性** | 法定記録として成立させる最低条件 |

### Phase 2 以降の候補

- 麻薬・向精神薬の使用記録と帳簿出力（**優先度高**。紙台帳の二重管理を潰せる）
- 飼い主向け入院レポート配信（写真・バイタル共有）
- 費用明細の積み上げと既存レセコンへのエクスポート
- 面会予約
- シフト管理との連動

### **作らないもの**（明示的に決定）

| 作らないもの | 理由 |
|---|---|
| 外来カルテ・レセプト・会計の本体 | 既存レセコンと正面衝突する。置き換えを迫ると導入が止まる |
| 診断支援、重症度の自動判定、治療方針の提案 | **動物用医療機器プログラムに該当するリスク**（`02-regulatory-requirements.md` §6） |
| オンライン診療機能 | 農水省指針の対象。Phase 1 で背負う必然性がない |
| ペット保険の窓口精算 | 保険会社ごとの仕組みで、単独では実現できない |
| 産業動物（牛・馬等）への対応 | 業務がまったく違う。ただし**保存期間8年の差だけはデータモデルに織り込む** |

> スコープを狭く保つことが最大のリスク管理。「電子カルテも作れますか」と言われても Phase 1 では断る。

## 4. 設計原則

### 原則1 — 記録は消えない、書き換わらない

法定記録である以上、`UPDATE` と `DELETE` を前提にしない。訂正は訂正として追記する。
アプリ用のDBロールから該当テーブルの更新・削除権限を剥奪し、**実装のバグでは壊れない**状態にする。

### 原則2 — 資格と権限はサーバで判定する

「このボタンを出さない」はUIの都合であって権限ではない。実施記録の登録可否は必ずサーバ側で資格を検証する。

### 原則3 — 入力の敷居を下げる。必須項目を増やさない

現場は片手でiPadを操作し、手袋をしていて、動物を押さえながら記録する。
**必須項目を増やすほど記録されなくなり、記録されなければシステムの価値はゼロになる。**
バイタルは1項目だけの記録を許す。あとから補完できる設計にする。

例外は、欠けると事故につながる項目（`dnrOrder`、`contactPolicy`、`skipReason`、`deviationReason`）。ここだけは必須にする。

### 原則4 — 計算はサーバで、丸めは最後に一度だけ

投与量計算は `numeric` で行い、浮動小数点を使わない。中間結果を丸めない。
クライアントの計算結果は保存しない。

### 原則5 — オフラインでも記録できる

院内Wi-Fiは落ちる。処置室は電波が悪い。**通信断でローカルに記録し、復帰後に同期する**設計を最初から入れる。
後付けは極めて困難なので、Phase 1 の段階でデータモデルに `clientRecordId`（クライアント生成のべき等キー）を持たせる。

### 原則6 — 既存レセコンと戦わない

「レセコンを置き換える」ではなく「レセコンの入院部分を強化する」と言う。
連携はまずCSVエクスポートから。API連携は相手次第なので期待値に織り込まない。

### 原則7 — UI文言で「診断」しない

`02-regulatory-requirements.md` §6 の通り、動物用医療機器プログラムの該当性を避けるため、
「異常」「危険」「〜の疑い」といった評価語を使わず、「基準範囲外」「上限を超えています」等の事実表現に留める。

## 5. 品質のライン

投与量計算にバグがあれば動物が死ぬ。以下は交渉の余地なし。

- 投与量計算ロジックは**単体テストのカバレッジ100%**、境界値・異常系を含む。
- 資格チェック、状態遷移の不変条件は、すべてテストで固定する。
- 本番DBへの直接操作を禁止する運用を最初から敷く。
- リリース前に、実際の処方例（少なくとも30ケース）で獣医師による計算結果の突き合わせを行う。

## 6. 進め方

```
[現在地] 定義フェーズ
  ├── 01 用語集              ← 完了
  ├── 02 法令要件            ← 完了
  ├── 03 ドメインモデル      ← 完了
  ├── 04 アクターとユースケース ← 完了
  ├── 05 市場と競合          ← 完了
  └── 06 未決事項            ← 完了（要: 実地調査と官庁確認）
        ↓
[次] 検証フェーズ ── 動物病院への実地ヒアリング（5件）／農水省への該当性確認
        ↓
[その後] 設計フェーズ ── DBスキーマ、API設計、画面設計、技術選定
        ↓
実装フェーズ ── ケージボード + 指示 + 投与量計算 + 実施記録 の順
```

**検証フェーズを飛ばさない。** 未決事項（`06-open-questions.md`）のうち #1（薬機法該当性）と #2（現場の実業務）は、実装に入る前に潰す。
